# AI 每日动态 · 2026-08-12

> 今日主线：**harness 昨天集体升格了——从「人手工调的部署产物」变成了可评测、可自进化、可迁移的一等公民。**
>
> 昨天 arXiv 那一批（cs.AI 486 篇 / cs.CL 171 篇）出现了一个几乎不像巧合的现象：**标题里带 "harness" 的论文一次性冒出六篇以上**，而且分别占住了这件事的不同侧面。① [Evo-Bench](https://arxiv.org/abs/2608.09096) 造了**第一个专门评测「模型能不能自己改进 harness」的基准**，把 harness 增益从基座模型强度里剥离出来测，最强模型绝对提升 **16.6 分**、逼近人类手工工程的 SOTA 基线；② [Ouroboros](https://huggingface.co/papers/2608.08311)（HF Daily Papers **1.09k 票**断层第一）把自我改进落到工程上——工具、提示词、上下文装配、核心实现全部通过**经评审的 commit** 进化，且这些 commit 就是后续工作的运行时，Terminal-Bench 2.1 拿到 **86.74%** 的榜单最佳；③ [OEO](https://arxiv.org/abs/2608.09629) 反过来问：**当优化器本身足够强，那套预设的优化流水线还有必要吗？** 14 组对照里 **12 胜 1 平 1 负**，token 只用规定式方案的 **34.3%**。
>
> 三篇拼起来是一句话：**harness 不再是你调好就冻住的配置，而是一个有自己的评测基准、有版本、能迁移、也能被模型自己改的软件系统。** 而 Evo-Bench 那个「合成出的 harness 是高度可迁移的推理结构，能稳定提升各种策略模型」的结论，直接给「值得花时间打磨 harness」这件事发了张背书。
>
> 配套还有两条护栏：[SkillSentry](https://arxiv.org/abs/2608.09253) 说 skill 文档不等于稳定执行（加运行时保障后成功率 **+24.1%**、方差还降了），[CoreBreak](https://pivotnews.ai/security/aws-google-and-vercel-patch-agent-flaws-that-bypass-the) 则用三家大厂的 CVE 证明**执行层不校验 tool call 的来源，模型层所有护栏都可以被绕过**。

### 论文（HF Daily Papers · Aug 10 批次）

- [Ouroboros: A Self-Developing Frontier Coding Agent with Reviewed Core Evolution](https://huggingface.co/papers/2608.08311) — **今日头条，1.09k 票断层第一。** 一个 harness 会自己改自己：工具、提示词、上下文装配、核心实现全部经由**评审过的 commit** 演进，而这些 commit 就成为后续工作的运行时。两种进化模式分得很清楚——**递归自由进化**（改进本身就是一个任务，跑完一轮可以调度下一轮）和**经验驱动的核心进化**（日常工作和社交互动暴露出 bug、粗糙边角、低效的上下文构造，进而触发结构性修改）。成绩：Terminal-Bench 2.1 **86.74%**（榜单最佳）、OSWorld-Verified **90.69%**（超过此前最佳）、CL-Bench 五轮归一化奖励 **0.2301**（新 SOTA）。最值得看的是 **Hope**：一个跑了 **161 天**的活体 agent 实验，在七个界面上接受受治理的人类沟通——**人类只负责暴露问题和提建议，改哪个由 agent 自己决定**。作者点出的核心设计难题也很诚实：**一个能改自己代码、还能自己换模型 API 的 agent，护栏必须在进化压力和公开社交压力下依然保持权威**；所以基准测试跑的是冻结快照，Hope 在另一条血脉上继续演化
- [Macaron-V1: Towards Open Continual Learning with Self-Improvement and Mixture-of-LoRA](https://huggingface.co/papers/2608.09819) — 212 票，49 页技术报告。和 Ouroboros 是同一件事的另一种做法：**「版本化的 模型—harness 配对」的递归改进**——一个配置产出的经验，在**外部契约**下被评估，然后用来构造它的后继版本。架构侧是 Mixture-of-LoRA：冻结基座、组合专家 LoRA、**每个用户轮次只选一个 LoRA**（旗舰 Venti 是 744B GLM-5.2 基座 + chat/agent/coding/GenUI 四个 LoRA；Tall 是 Qwen3.6 基座 50B 供本地部署）。名词值得记住：**Model-Harness Co-design**、**versioned HCP contract**、组件原生的 GenUI harness「UI4A」、有状态动作基底
- [BDH-CQ: In-Context Learning with Recurrent Latent Reasoning](https://huggingface.co/papers/2608.09888) — 239 票。反直觉得很干净：**150M 参数**配置在 ARC-AGI-1 公开评测集上拿到 **29.5% pass@2**，每题推理成本 **$0.0007**，**直接突破了此前 ARC-AGI-1 的成本—准确率帕累托前沿**。做法是推理期输入持续更新模型的循环记忆，然后在高维隐空间里迭代计算求解，**中间推理不出声**（不 verbalize）。对「必须靠长思维链堆 token 才能推理」这个默认假设是个有力的反例
- [SWE-Bench ProMax: Benchmarking Agents on Large-Scale Multilingual Code Refactoring](https://huggingface.co/papers/2608.09802) — 116 票。抛出的那个审计结论比基准本身更值得警惕：**近 60% 未解的 SWE-bench Verified 实例，测试是有缺陷的**——要么过窄（拒绝正确解），要么过宽（检查了题目没说的要求）；而且前沿模型**能逐字复现训练数据里的 gold patch**。新基准改测**代码重构**（跨多文件、行为保持的协同改动），170 个实例取自七种语言（Python/Java/TypeScript/Go/C/C++/Rust）的真实 commit，问题描述全部重写、测试逐条人工复核

## 【arXiv 精选】

> 来源：arXiv cs.AI / cs.CL 当日新提交（**Tue, 11 Aug 2026 批次**，cs.AI 486 篇 / cs.CL 171 篇）。今日只有一条主线：**harness 的自我进化，以及为它配套的评测、护栏与记忆结构。**

- [Evo-Bench: Can Language Models Improve Agent Harness?](https://arxiv.org/abs/2608.09096) — **今日必读第一篇。** 现有评测全都停在静态任务求解上，而作者认为下一个前沿是 **harness evolution：agent 自主优化自己运行环境的能力**。难点是怎么把 harness 的增益从基座模型强度里剥出来、怎么防止对特定任务过拟合、怎么捕捉长周期迭代研究——Evo-Bench 用**辅助任务进化**先筛出「真正对框架改进敏感」的任务，再做**敏感度感知的分层切分**保证跨套件泛化，覆盖 Search / Office / General 三个域。九个前沿及开源权重模型的结果有三条特别实用：**① 最强模型绝对提升达 16.6 分，已逼近人类手工工程的 SOTA 基线**；**② 自主进化在 General 域超过人工 harness、在 Search 域尤其强，但在 Office 这类需要高度特定处理流程的任务上明显吃力**（说明领域知识密集的流程还得人写）；**③ 合成出的 harness 是高度可迁移的推理结构，能稳定提升多种不同的策略模型**——这条等于说你打磨 harness 的收益不会被换模型清零
- [Rethinking Self-Evolving Agents: Do We Still Need Prescribed Optimization Pipelines?](https://arxiv.org/abs/2608.09629) — **今日必读第二篇，问题问得很狠。** 自进化 agent 通常围绕预设的优化流水线搭建：框架决定怎么收集证据、怎么修订持久化产物、怎么选候选、什么时候停。作者提出 **Open-Ended Optimization（OEO）**——目标、允许的交互、资源预算、数据边界、评估方式全部固定不变，**唯独让优化器在线自己组装改进过程**。在 8 个「基准 × 目标模型」设置上做 14 组对照，GPT-5.5 驱动的 OEO **12 胜 1 平 1 负**（唯一那次输只差 0.21 个百分点），token 中位数只用规定式方案 SkillOpt 的 **34.3%**；一次性零交互的对照组证明这不是「靠先验一把重写」蒙来的。但**委托是有能力边界的**：换成中等优化器，SkillOpt 反超；弱优化器根本没法通过 OEO 那个不变的接口工作。结论一句话——**规定式流水线是「依赖能力的脚手架」：硬性约束必须留在外部，但足够强的优化器可以自己组装从反馈到持久改进的那条路线**
- [SHE: Trajectory-driven Safety Harness Evolution for LLM Agents](https://arxiv.org/abs/2608.09885) — 把「安全」也纳入 harness 进化，而且**拆解方式可以直接拿去用**：agent 安全不只取决于权重，还取决于管理上下文、记忆、工具、权限和运行时控制的那层 harness；现有机制却把 harness 当成固定的部署产物，且组件间功能耦合导致**安全责任无法归因**。SHE 把 harness 拆成四件职责明确的工件——**System Prompt / Rule Bank / Safety Memory / Tool Policy**，从而支持局部进化；再用归因引导的进化循环把轨迹失败转成结构化诊断、学出针对具体工件的边界细化、通过安全—效用双重验证来选型。Agent-SafetyBench 上攻击成功率相对静态 SafeHarness **降低 3.1 倍**，**同时良性任务效用还提升了**；进化出的 harness 能泛化到未见风险（AgentHarm 留出集），并**无需重新进化即可跨 agent 模型迁移**。[代码开源](https://github.com/RainbowQTT/SHE)
- [SkillSentry: Reliable Skill Execution for LLM Agents via Runtime Assurance](https://arxiv.org/abs/2608.09253) — **写 skill 库的人今天最该看的一篇。** 复旦团队指出一个被普遍忽略的事实：**skill 提供了可复用的过程性知识，但不保证执行稳定**——即使 agent 已经证明它能在某个 skill 指导下完成任务，它也可能在相似任务或重复运行中做不到，原因是偏离了 skill 流程或者某一步执行错了。SkillSentry 用一套**新的 DSL 来表达「skill 执行的运行时指导」**：先把 skill 文档抽出的规格 + 历史成功/失败轨迹挖出的执行经验合成初始指导，然后**包在 agent 执行循环外面**做监控与引导，同时用新收集的轨迹迭代细化指导。在 15 个 skill × 两个 agent（Claude Code 配 Haiku-4.5/Opus-4.6、Codex 配 GPT-5.2/5.4）上，**任务成功率平均 +24.1%，且重复运行的方差更低**
- [From Prompt to Harness: Coderlet from Scratch](https://arxiv.org/abs/2608.09480) — 想搞懂 harness 到底是什么的最短路径，而且**有可执行产物**。作者顺着**一个请求**走完全程：上下文形成 → 模型决策 → 环境动作 → 观测返回 → 状态延续，据此提炼出三条边界——**model / execution / state**，分别连接模型服务、工具环境和持久状态，而请求生命周期决定这些转换的顺序。三句话概括 harness 的核心职责：**把模型生成转成环境动作、把运行时反馈带进后续决策、让状态跨请求延续**。这套设计落成了[开源实现 Coderlet](https://github.com/lilinxi/Coderlet)（正文只 33KB，极适合精读）
- [Tree-of-Experience: Hierarchical Experience Management for Self-Evolving Agents](https://arxiv.org/abs/2608.09044) — 现有经验管理要么精修单条轨迹、要么从相关轨迹里抽象共享知识，**问题在于经验表示和底层推理过程是脱节的**，于是反馈归因、跨任务迁移、更新与检索效率全都受限（在只有结果级反馈的复杂推理任务上尤其明显）。ToE 的做法是让**经验的组织结构对齐 agent 的层级推理过程**：组织成一棵共享的「分析视角 + 推理路径」树，其可靠性由环境结果校准。Game of 24 上相对无经验的 ToT 基线准确率**相对提升 31.4%**；FinEvolveBench 的 12 个设置上 tsIC **平均提升 41.24%**——而对照组里**传统经验管理方法经常还不如「完全不用经验」**，这个反差本身就是个警告
- [RoMeRL: Balancing Feedback Coverage and the Memory-Reward Trap in Self-Evolving Agent Memory](https://arxiv.org/abs/2608.02508) — 学习型记忆系统的两个死结，说得很透：**① 以轨迹索引的效用会随交互历史一直膨胀**，把本就有限的反馈摊薄到不断扩张的状态空间上；**② 轨迹级奖励是共同分给一批被同时检索出来的记忆的**，于是无关经验也会收到误导性的效用更新——作者称之为 **memory-reward trap**。RoMeRL 改用**固定维度的每任务记忆状态**（按结果极性和记忆动态做因子分解）来表示那个膨胀的效用空间，新经验通过一组**固定的语义坐标**接入、内容随时间更新或替换，从而把反馈集中在有界的效用支撑上。ALFWorld 和 LifelongAgentBench 上：**Cold-Q 比例降 80.0%、反馈密度约提升 6 倍、维护的记忆体积降 84.4%、LLM 调用降 21.1%**。[代码开源](https://github.com/YOUNG-fnxm/RoMeRL)
- [Consilience for Verifier-Free Test-Time Scaling](https://arxiv.org/abs/2608.09898) — 现实里往往拿不到编译器、测试用例、价值函数这类高质量验证器，所以纯靠置信度排序的 VF-TTS 很受欢迎（开销近零、几乎不需要访问模型内部状态）。作者先证伪它：**这类方法在复杂任务上会灾难性失效**，而且现象很有意思——**普遍偏高的置信度往往说明模型没在探索，于是偏向「自信地答错」**。核心洞察是稳健的认知搜索有一条特定的置信轨迹形态：**开头低置信（在做探索性分叉），结尾高置信（收敛到解）**。Consilience 就把这个「置信度的时间不对称性」做成组合度量——**主动惩罚开头就高置信，同时严格要求结尾确定**，在研究生级数学和自由形式代码生成上都超过现有基线。**「看轨迹形状而不是看终值」这个思路，对做路由和早停判据的人可以直接迁移**

## 【前端 → AI Agent 转型方向】

### 框架 / 工具链

- [Stagehand v4：浏览器 agent 终于说前端母语了](https://www.browserbase.com/blog/stagehand-v4) — **今天前端最该动手试的一个。** 给浏览器 agent 提供 **Playwright 风格的 API**，你用熟悉的浏览器自动化命令写 Web 交互，同时它以**浏览器扩展形态运行**来压低延迟。官方数据：比 Playwright **快约 2 倍、token 效率高约 80%**，具备**自我修复动作**（页面元素移动或改变后能恢复），并且**支持嵌套 iframe 和 Shadow DOM Web 组件**——最后这条是同类工具长期的痛点。开源 SDK，且**四个主流框架都有官方集成包**：[Vercel AI](https://github.com/browserbase/stagehand/tree/main/packages/integrations/vercel-ai#readme) / [Mastra](https://github.com/browserbase/stagehand/tree/main/packages/integrations/mastra#readme) / [DeepAgents](https://github.com/browserbase/stagehand/tree/main/packages/integrations/deepagents#readme) / [CrewAI](https://github.com/browserbase/stagehand/tree/main/packages/integrations/crewai#readme)
- [n8n Agents：agent 从工作流里独立出来了](https://docs.n8n.io/build/build-and-manage-agents) — 架构变化比功能清单重要。此前的 AI Agent 节点定义在**某一个工作流内部、只在该工作流运行期间存在**；新的 Agent 定义**一次**、住在工作流旁边自己的标签页里，**自带 model / instructions / tools / memory / sessions**，然后在多处同时使用——聊天、接 Slack/Telegram/Linear、定时跑，或者用新的 `Message an Agent` 节点从任意工作流调用。三个细节很对味：**你现有的工作流会变成 agent 可选的工具**；**有草稿版和发布版**，编辑时线上照常跑；**工具可以标记为需审批**，敏感操作会等你点头。目前是 Preview（需 2.32.3+，最好 2.34.x，且分批灰度到 50% 用户），连续事件流监听和完整多 agent 编排还没有
- [CoreBreak：AWS / Google / Vercel 同时被打穿，模型压根没运行](https://pivotnews.ai/security/aws-google-and-vercel-patch-agent-flaws-that-bypass-the) — **做 harness 的人今天必须读的一条。** Black Hat USA 2026 上披露的同一类缺陷：SDK 正常流程是「请求+系统提示+历史+工具定义 → 模型 → 结构化的工具调用指令 → 执行」，而**这些实现没有校验最后两步之间的 provenance——任何长得像模型生成的 tool call 都被当成权威**。于是攻击路径里**模型往往完全没运行**，系统提示、内容过滤、模型级护栏全部没有介入机会。受影响的是 Bedrock AgentCore 的 InvokeHarness（CVE-2026-18830，CVSS 8.6）、Google Python ADK（CVE-2026-18236，CVSS 9.3，伪造人工审批）、以及 **Vercel AI SDK 的 harness 包**（`@ai-sdk/harness-codex` / `-opencode`，CVE-2026-64650/64651）——后者是 relay 只要看到命令行里含批准过的 helper 脚本路径就信任该进程，沙箱内的恶意依赖或构建脚本即可借此调用宿主工具（含密钥查询、部署操作、云 API）。Vercel 的修法值得抄：**去掉进程路径回退，只接受与模型事件中观测到的工具名和输入精确匹配的、短时效、一次性的授权**。一句话记住——**任何只写在系统提示或模型响应里的防护，在调用方能绕过模型轮次直达 dispatch 时就等于不存在**
- [Vercel Chat SDK 的 durable approvals](https://www.developersdigest.tech/blog/vercel-chat-sdk-durable-approvals-2026) — 8/6 上线的 `requestApproval`：把「等人点头」做成可持久化的挂起（底座是 Workflow SDK 的 durable execution），原先要三个系统拼的审批层现在一次调用。作者提醒的失效模式对做 UI 的人更重要——**审批疲劳本身是个安全 bug**：如果五步工作流每步都要在聊天里点一下，你只是换了个姿势重新引入疲劳。正确形状是**风险感知的自主性 + 审批只留给不可逆动作**

### 学习资源

- [Harness Engineering：为什么最强的 AI 也需要一个操作系统](https://agentpatterns.ai/agent-design/harness-engineering/) — **今天最完整的一份 harness 方法论，而且是英文原始出处。** 三大支柱：**Legibility**（仓库即唯一事实源，AGENTS.md 当约 100 行的精简索引，渐进式披露而非一个巨型指令文件）、**Mechanical Enforcement**（自定义 linter + 结构测试 + CI 门禁，**错误信息里要写补救方案而不只是报错**）、**Constrained Solution Spaces**（用工具锁定唯一合法的导入方向，而不是在文档里请求遵守）。另一半是 Xu et al. (2026) 的**四层运行时适配面**：Environment Contract（首次行动前明确约束、策略、工具规则、已知坑）/ Procedural Skill（从轨迹提炼的技能库，检索式非参数引导）/ Action Realization（模型输出与环境之间的闸门，校验可执行性、规范化接口错误、拦掉确定会失败的动作）/ Trajectory Regulation（执行后监控重复、停滞、预算耗尽）。**数字很有说服力**：126 个模型—环境设置中 **116 个提升**、跨 18 个 backbone **平均相对 +88.5%**，且**从单个 4B 模型演化出的 harness 能迁移到另外 17 个模型**；LangChain 那边**只改 harness 不换模型**，Terminal Bench 2.0 从 **52.8% → 66.5%**。同样重要的是「什么时候不划算」那一节：**过度约束会逼 agent 扭曲实现**（Vercel 的经验是全量工具库反而不如精简版）、**单体指令文件会腐化成噪声**、短命代码库不值得建这套
- [淘宝直播助手 Agent Harness 实战](https://juejin.cn/post/7671566723838394406) — **中文世界里最好的 harness 落地案例，而且处处能看到前端的影子。** 六层结构可以直接拿去对照自查缺哪块：**Loop → Tool → Context → State → Hook → Eval**。核心思想一句话：**业务方专注写 Skill，框架层兜住所有其他脏活**。几个直接可抄的设计：**Reducer 模式**——不再把每轮工具调用的完整 JSON 追加进历史让模型自己推断状态，而是借前端状态管理的思路做职责分离（**模型只负责决策，Reducer 纯函数负责状态变更**），每轮把最新结构化状态序列化后注入，模型看到的是一份干净确定的快照；**三类资产分库**（记忆存 Hologres 做混合检索、**Skill 存 GitLab 走 Code Review 和灰度发布**、会话存 MySQL）；**Hook 挂在五个时机**（PreReasoning 注入上下文 / PreToolCall 安全拦截 / PostToolCall 触发 Reducer / PostReasoning 幻觉检测 / OnSessionEnd 记忆回写）；**写操作强制幂等键**，避免重试或重规划造成「双改价」；**大上下文卸载**（存对象存储，在隔离沙箱里跑筛选命令，只回精简摘要）
- [2026 年五大 Agent 框架横评：只看「第二天」的表现](https://devops-daily.com/posts/top-5-ai-agent-frameworks-2026) — 评判标准立得很好：**「能在循环里调模型和工具」早就不稀奇了，区别在第二天**——进程跑到一半重启会怎样、工具需要人审批时怎么办、别人问「它为什么那么做」你能不能答、以及你怎么证明改了 prompt 之后是变好而不是变差。结论：**Mastra 第一**（TS 团队想要一体化栈：durable workflow + memory + evals + tracing 不用拼四个库）、**LangGraph 胜在控制粒度和生态深度**、**Vercel AI SDK 仍占据流式和 UI 的高地、agent 原语也补齐了，但没有 durable workflow 引擎**。数据取自 2026-08-11 的 GitHub/npm：AI SDK 周下载 **2055 万**（断层第一），Mastra 27.1k stars / 134 万，LangGraph 39.4k / 324 万。作者特别声明**排名不是 star 数排序**——星数最多的那个根本没进前五

### 实践案例

- [Xirp：Spotify 给编码 agent 造了「机构记忆」](https://xirp.spotify.com/) — 解决的问题非常具体：**每个 agent 会话都从空白开始，公司上下文得重新喂一遍**。Xirp 把服务、归属、文档、架构决策沉淀下来，让会话启动时自带这些。**Spotify 内部已有 1300+ 工程师在用**。这条和昨天那批「记忆」论文是同一件事的两端：论文在研究记忆的效用归因和撤销机制，工业界在解决「记忆从哪来、谁维护」
- [Databricks：把内部 AI 编码开支砍掉最多 90%](https://www.databricks.com/blog/managing-ai-coding-costs-scale) — 四个手法都不玄学：**默认用便宜模型、任务级路由、给用户看得见的预算、激进地裁剪上下文**。同一篇里还有个对照数据值得记：极简 harness [**pi**](https://github.com/badlogic/pi-mono)（只 4 个工具 + **不到 1000 token 的系统提示**）在 Databricks 的测试里**发送的上下文约少 3 倍，却以更低成本拿到比 Claude Code 或 Codex 更高的通过率**。和 AgentPatterns 那条「全量工具库不如精简版」互为印证——**工具越多不等于越强，选择少反而更快更可靠**
- [极小本地 harness 的两个新样本：Ante 与 Needle 2](https://github.com/AntigmaLabs/ante) — [Ante](https://github.com/AntigmaLabs/ante) 把编码 agent harness 打包成约 **15MB 的 Rust 二进制**，内嵌工具 + 内置 llama.cpp + 多提供商支持 + 终端 UI + 服务器模式 + 多 agent 技能，**完全离线跑 GGUF，无运行时依赖也无模型锁定**；[Needle 2](https://cactuscompute.com/needle) 更极端——**45M 参数**的 agentic 模型压成 **14MB 二进制、会话 RAM 约 28MB**，专做工具调用、设备控制和结构化提取，手机 / VR / 树莓派可跑，Apache 2.0。这两个放一起说明一件事：**harness 的体积和模型的体积正在同时向下探底，「本地 agent」的门槛已经低到嵌入式级别**

## 今日值得深入

**1. 把 Evo-Bench + Ouroboros + OEO 当一组读 —— 这是 harness engineering 的「立法之日」**

昨天这三篇同时落地，恰好回答了 harness 的三个层级问题：[Evo-Bench](https://arxiv.org/abs/2608.09096) 回答**「harness 的改进能不能被独立测量」**（能，而且把它从基座强度里剥离出来测之后，最强模型绝对提升 16.6 分、逼近人类手工 SOTA）；[Ouroboros](https://huggingface.co/papers/2608.08311) 回答**「harness 能不能自己改自己」**（能，走经评审的 commit，Terminal-Bench 2.1 86.74%，而且有个跑了 161 天的活体部署 Hope 摆在那）；[OEO](https://arxiv.org/abs/2608.09629) 回答**「那我们还需不需要写死那套优化流水线」**（强优化器不需要，12 胜 1 平 1 负、token 只用 34.3%；但中等和弱优化器仍然需要——**规定式流水线是依赖能力的脚手架**）。

对你手上那套 pi harness 实践，这组论文给了三个具体判断：

**① 打磨 harness 的收益不会被换模型清零。** 这是 Evo-Bench 最实用的一条结论——合成出的 harness 是**高度可迁移的推理结构**，能稳定提升多种策略模型；AgentPatterns 引的 Xu et al. 也是同一个方向（**从单个 4B 模型演化出的 harness 迁移到了另外 17 个模型**）。你写 AGENTS.md、定 skill 格式、约定 prompt 骨架，这些资产是跨模型的。

**② 但「哪部分该自动进化、哪部分必须你自己写」现在有答案了。** Evo-Bench 那条被忽略的发现很关键：**自主进化在 General 域超过人工 harness、Search 域尤其强，却在 Office 这类需要高度特定处理流程的任务上明显吃力**。翻译成你的场景——**通用的循环控制、上下文装配、错误恢复可以交给模型迭代；而领域特定的工作流（比如某个具体业务的操作顺序和验收标准）仍然得人写**。OEO 那句「essential constraints remain external」说的是同一件事：**约束留在外面，路线可以让优化器自己组装**。

**③ 自进化必须先有护栏，否则是在给自己挖坑。** Ouroboros 作者自己点出来了：一个能改自己代码、还能自己换模型 API 的 agent，**护栏必须在进化压力和公开社交压力下依然保持权威**，所以它跑基准用冻结快照、让 Hope 在另一条血脉上演化。两条配套读物：[SHE](https://arxiv.org/abs/2608.09885) 给了安全侧的进化单元划分（System Prompt / Rule Bank / Safety Memory / Tool Policy 四件工件各自负责、可局部进化、责任可归因，ASR 降 3.1 倍且效用还升），[SkillSentry](https://arxiv.org/abs/2608.09253) 给了执行侧的兜底（**skill 文档 ≠ 稳定执行**，包一层运行时指导后成功率 +24.1% 且方差更低）。

最后必须加一条硬约束：[CoreBreak](https://pivotnews.ai/security/aws-google-and-vercel-patch-agent-flaws-that-bypass-the) 证明 **AWS、Google、Vercel 三家的 harness 都犯过同一个错——执行层不校验 tool call 的来源**，于是攻击路径里模型压根没运行，系统提示和模型级护栏全部形同虚设。Vercel 的修法就是你的验收标准：**只接受与模型事件中观测到的工具名和输入精确匹配的、短时效、一次性的授权**。

**2. [淘宝直播助手 Agent Harness 实战](https://juejin.cn/post/7671566723838394406) + [AgentPatterns 的三支柱四层面](https://agentpatterns.ai/agent-design/harness-engineering/) —— 前端最短的落地路径，一份中文实战 + 一份英文方法论**

这两篇配着读的价值在于：AgentPatterns 给的是**该有哪些层**（三支柱 + 四层运行时适配面），淘宝那篇给的是**这些层在一个高风险生产场景里长什么样**（Loop / Tool / Context / State / Hook / Eval 六层）。

对你尤其顺手的是淘宝那套设计几乎全是前端思维的迁移：**Reducer 模式**——不把工具调用的原始 JSON 追加进历史让模型自己推断状态，而是**模型只负责决策、Reducer 纯函数负责状态变更**，每轮注入一份干净确定的状态快照。这就是 Redux 那套东西搬到 agent 循环里，而且解决的正是「上下文膨胀 + 状态判断出错」这个双重问题。**Hook 挂在五个时机**（PreReasoning 注入 / PreToolCall 拦截 / PostToolCall 更新状态 / PostReasoning 幻觉检测 / OnSessionEnd 记忆回写）本质是中间件洋葱模型；**Skill 存 GitLab 走 Code Review 和灰度发布**是把技能当代码管；**写操作强制幂等键**是幂等设计的老本行。

配套的落地节奏 AgentPatterns 也给了，务实得可以直接排进日程：**信息层 1–2 天**（写 AGENTS.md ≈100 行 + 结构化 docs/，收益是输出一致性明显改善）→ **约束层 3–5 天**（linter + CI 架构约束，**错误信息里写补救方案**）→ **自动化层 1–2 周**（agent 自验证闭环，人工审查量大幅下降）。最后别忘了那节「什么时候适得其反」：**过度约束会逼 agent 扭曲实现**、**单体指令文件会腐化成噪声**、**harness 需要按代码库变化速率主动维护，否则从资产变成负债**。
