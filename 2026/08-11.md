### 论文（HF Daily Papers · Aug 10 批次）

- [DCAS: Decoupling CLI Agent Scaffolding to Internalize Planning across Scaffolds](https://huggingface.co/papers/2608.06113) — **今天对做 harness 的人最有价值的一篇。** 现象很扎心：开源生态的 CLI agent 微调数据**几乎全部采自 OpenHands 一个脚手架**，于是这些模型在 OpenHands 下分数漂亮，**换任何非训练脚手架就大幅退化——而未微调的基座模型没有这个现象**，说明退化是微调引入的、绑死在训练脚手架的约定上。作者把「规划」拆成两义：**显式规划**（执行前产出的一等公民计划产物）和**隐式规划**（贯穿 agent 循环的结构性约定）。DCAS 是一层不改脚手架的后端替换拦截层，任意 CLI 脚手架 ↔ 任意后端模型自由组合，用它做的对照实验证明**规划质量的增益超过跨脚手架的掉分幅度**；只用少量 DCAS 采集的「规划感知轨迹」微调，就能在非训练脚手架上普遍提升
- [Beyond Simply Environment Scaling](https://huggingface.co/papers/2608.03571) — 中科院自动化所（28 票）。直接证伪「环境池越大越好」：单纯堆多模态训练环境数量**并不总是有收益**。改从两个维度设计环境分布——**多样性**用 Ability-aware Environment Selection 选，**难度结构**用 Hierarchical Difficulty Curriculum 组织（两级难度：**harness 弱化** + 状态规模递进）。[代码已开源](https://github.com/GaryStack/Beyond-MMEnv-Scaling)
- [SFT Conflicts, RL Coexists: 多任务学习的理论与实证分析](https://huggingface.co/papers/2608.03573) — 今日榜首（32 票）。同一批数据上，**SFT 的多任务目标彼此冲突，而 RL 的可以共存**——如果你在同一个 agent 上既要工具调用又要长文推理，这篇决定你该用哪种后训练配方
- [When Privileged Guidance Misaligns](https://huggingface.co/papers/2608.05219) — 多轮 agent 训练里，教师给的「特权引导」和学生当前状态对不上时会反噬，方案是状态匹配路由 + 上下文自蒸馏。和今天 arXiv 的 AMD「教师有效性同时取决于教师能力与师生兼容性」互为印证

## 【arXiv 精选】

> 来源：arXiv cs.AI / cs.CL 当日新提交（**Mon, 10 Aug 2026 批次**，cs.AI 201 篇 / cs.CL 76 篇）。今日两条主线：**小模型 agent 的记忆工程**，以及**推理算力的显式分配**。

- [Agent Memory Distillation: Empowering Small LLM Agents with Hierarchical Teacher Memory](https://arxiv.org/abs/2608.07169) — **今日必读，和 Muse Glimmer 是绝配。** 小模型做 agent 的死结是：它自己跑不出足够多的成功轨迹，所以「记忆系统」这套东西对它一直没用。AMD 是个**完全免训练**的框架，把大教师 agent 的成功轨迹拆成三种互补记忆：**Workflow memory**（任务级策略）、**Subtask memory**（中等粒度的具体行为示例）、**Function memory**（每个函数的调用约定和常见坑）。前两种在任务开始时**主动注入**，Function memory 在**工具调用报错时才反应式检索**。用 GPT-5-mini 当教师、四个 4B–8B 学生模型，在 AppWorld / BFCL V3 / ToolSandbox 上平均提升 **+27.2 / +11.2 / +3.4 个百分点**，全面超过已有记忆基线。三个附带结论很实用：**Subtask memory 贡献最大**；教师有效性同时取决于教师能力**和师生兼容性**；**4B 学生受益最大**
- [CoBa: Cost-Effective Test-Time Scaling via Compute-Balanced Routing](https://arxiv.org/abs/2608.07424) — **和你那套三层路由几乎是同一个问题的论文版。** 论点：test-time scaling 通常只沿一个轴加码（多采样 / 拉长思维链 / 换更强评估器），但**在固定预算下这三者是互相竞争的**。CoBa 把它显式建模成算力分配问题——下一单位算力该花在生成、验证，还是停止？做法是先出一小批候选，**便宜验证广撒网，只把不确定或高价值的候选路由给强验证器**。在 MATH-500 / AIME 2024·2025 / AMC 2023 + 程序化符号推理共 3,129 次评测上：宏平均 **85.13%**，与自评加权投票的 85.20% 统计上打平，但**参数加权 token 少 49.1%**；与 best-of-16 多数投票宏准确率差距在 0.01 以内，**token 少 58.9%**。作者最后那句话可以直接抄进你的路由设计文档：**「对本地推理系统而言，test-time scaling 就是在问下一步算力花在哪最值。」**
- [TEPA: Revoking Stale Memories for Conflict-Robust Language Agents](https://arxiv.org/abs/2608.07429) — 长期记忆的一个致命且被普遍忽略的失效模式：**世界变了，过期记忆仍然可被检索，于是污染 prompt**。作者称之为 memory pollution，并把「有效性」提升为记忆的**显式状态**——观测存成带 key 的先例，同 key 下有新证据反驳时**撤销（revoke）旧先例**，检索只取当前有效证据，但**撤销记录保留下来供审计和后续重新启用**。数字很吓人：受控漂移 50 个种子下发生完全反转时，append-only 和 last-write-wins 都只有 **0.210，比「完全不用记忆」的 0.309 还差**，TEPA 是 **0.950**；真实文件执行漂移下复现同一模式。在干净的 MemoryAgentBench SH-6k 上 TEPA 与强 last-write-wins 缓存持平——说明**单跳事实固化靠的就是同 key 替换这一个操作**
- [The Horizon Gap: Planning, Memory, Execution, Training, and Evaluation for Long-Horizon LLM Agents](https://arxiv.org/abs/2608.06663) — 39 页综述，**系统梳理了 1,547 篇 2024–2026 的 arXiv 论文**（含公开披露的 26.8% 误收率过滤）。最有价值的是它把三个被长期混用的概念掰开了：**long-horizon 是任务属性**（需要多少步）、**long-context 是模型属性**（token 容量）、**long-term memory 是系统属性**（跨步/跨会话的持久化）。全文六大类横切一条「horizon 存放在哪」的轴（上下文内 / 任务内超上下文 / 跨任务持久）。跨所有类别的共同结论只有一句：**horizon 一长，只看最终结果的信号就迅速失去信息量，于是整个领域都在造更密的步级信号**——过程奖励模型、信用分配、轨迹级诊断，本质是同一件事
- [SkillProx: Self-Evolving Agent Skills via Proximal Textual Gradient Descent](https://arxiv.org/abs/2608.07449) — 港科广。技能自进化的两个缺口：缺**诊断—结果的闭环反馈**，以及把「删除」当成普通编辑操作而不是知识固化的专门机制。SkillProx 借近端梯度的前向—后向结构：前向阶段在**同一批任务上重跑**诊断驱动的编辑、**回滚劣化**、把实测结果喂回下一轮诊断；后向阶段把技能拆成可审计的知识单元，用**冻结的留一法效用审计**估贡献，再做验证门控的固化 / 降级 / 移除。比最强的梯度式基线平均高 3.0 个百分点。**「留一法审计 + 回滚劣化」这两个动作，对手写 skill 库的人也直接可用**
- [CoinRAG: Contextualized Information Nugget KV Cache Reuse for Long-Context RAG](https://arxiv.org/abs/2608.07458) — 现有做法是切块级 KV cache 复用，但粗粒度块里冗余和噪声还在。CoinRAG 改成**细粒度语义单元（nugget）的离线 KV 缓存组合复用**：两阶段检索定位块内与查询相关的语义单元，把它们的 KV 切片和块级上下文拼起来。LongBench 多跳问答上在标准快速 prefill 预算下 F1 **相对提升 5.3%**，并推出新的帕累托前沿。**「预算约束下的帕累托前沿」这个提法，比单纯比准确率更适合做工程决策**

## 【前端 → AI Agent 转型方向】

### 框架 / 工具链

- [Mastra 1.56.0：工作流从代码变成数据](https://releases.sh/release/rel_PSUgFTmO7fOP-LhRUWUj1) — 8/5 发布，这版的方向性很强。**可持久化的声明式工作流**：工作流现在能被写成数据，通过 `toStorableGraph()` / `rehydrateWorkflow()` 在 JSON 里往返，于是**由 UI 或 LLM 构造的工作流图能扛住进程重启**；新增 `.agent()` / `.tool()` / `.map()` 三种一等公民步骤类型（不再被 `createStep` 包成不透明的通用步骤），且**编译期强制输入输出 schema 链式校验**。配套的还有 stored workflows 全链路（HTTP `POST/GET/DELETE /stored/workflows` + `@mastra/client-js` 的 StoredWorkflow 资源 + 各主流数据库适配器的 `workflowDefinitions` 域）、用结构化谓词 DSL 表达条件与循环（取代只能闭包的写法，因此可持久化）、以及 evals 侧的 `unmockedToolPolicy`（**拒绝未声明的工具调用**）。**「工作流是数据不是代码」这一步迈出去，agent 编排就能被前端可视化编辑了——这是前端最该盯的接口变化**
- [Vercel 上线 skill packs（skills.sh）](https://www.my2cents.ai/news/2026-08-05-vercel) — 把多个 agent skill 打成一个可分享的包，一个 URL 或一个 GitHub org 就能分发，`npx skills add` 安装、`npx skills update` 更新。**团队里 agent 能力的标准化终于有了 npm 式的分发方式**。同批还有 `@ai-sdk/workflow@1.0.52`：**同一 workflow step 里有工具暂停等待客户端执行或审批时，其他已完成工具的结果现在会照常流式返回**——以前一个暂停会把整步的可见性全堵死，这个修复对做审批流 UI 的人是刚需
- [Vercel AI Gateway 与 Sandbox 接入 Hermes Agent](https://www.my2cents.ai/news/2026-08-08-vercel) — Gateway 给 agent 一个统一接口访问 200+ 模型（统一计费 + 跨供应商故障转移），Sandbox 给它隔离的 microVM 跑命令。信号很明确：**Vercel 在把自己的原语定位成「别人家 agent 产品的底座」，而不只是驱动自家工具**。同日还把 `@ai-sdk/xai@4.0.31` 从 openai-compatible 通用层里拆出来重写——**通用兼容层会抹平各家特有的工具调用行为，这个坑值得记住**
- [MCP 规范 2026-07-28：传输层彻底无状态化](https://vocolife.com/news/mcp-stateless-updates-scaling-ai-agent-infrastructure-245122) — 自发布以来对 MCP 最大的一次改动。2024 年的原始设计面向单客户端—单服务端，**有状态设计在云原生扩容时成了瓶颈**；Google 联合 HF 等成立 MCP Transports Working Group，新规范移除传输层会话管理，**让 MCP 能跑在普通的 HTTP 负载均衡设施上**。如果你在写 MCP server，这条决定你的部署形态

### 学习资源

- [AI 时代来临，前端如何转型 Agent 开发](https://damodev.csdn.net/6a79327910ee7a33f298d6f8.html) — 五步递进路径，每步都有明确的完成信号：**① 带流式输出的对话页**（搞清请求发起、流式返回、中断处理、生成过程展示）→ **② 加结构化输出**（让模型返回固定 JSON：意图、任务类型、置信度、追问、下一步动作，然后用代码消费它）→ **③ 接入一个真实低风险工具**（查天气 / 查文档 / 读本地文件，这一步就跨过了聊天机器人和 Agent 的分界）→ **④ 做一个垂直场景 Agent**（前端报错排查助手、接口联调助手这类，而不是「万能助手」）→ **⑤ 补权限、日志和二次确认**（这一步决定它是 Demo 还是能进业务系统）。作者点的两个坑也准：**把 Agent 做成万能助手**（没有边界比规模小更致命）、**只关注模型不关注系统**（第一反应是换更强模型）。另外那句 SQL 建议值得抄进护栏清单——**别让模型直接拼 SQL 执行，给它受控的查询工具或只读且限权限的数据视图**
- [本地跑 AI Agent 的完整配置指南（Ollama + OpenClaw）](https://www.remoteopenclaw.com/blog/local-ai-agent-setup-guide) — 十分钟从零到能跑工具调用的本地 agent。比步骤更有用的是那份**诚实的权衡清单**：小模型在工具调用上**更容易生成畸形 JSON、幻觉工具名、传错参数类型**，所以要预留更多重试和错误处理；硬件是一次性前置投入（Mac Mini 24GB 或 RTX 4090，$500–2000），**每天只跑几个任务的话云 API 反而更便宜**；以及「本地 ≠ 自动安全」——机器本身、访问控制、输出处理仍然要管

### 实践案例

- [Owning Your Private AI Assistant：零后端的浏览器本地助手](https://seehiong.github.io/posts/2026/08/owning-your-private-ai-assistant) — 8 月新开源的 Local AI Starter，**100% 客户端、零后端**：WebGPU 跑推理，模型权重缓存在 OPFS（降级到 Cache API），会话/消息/长期记忆三张表全在 IndexedDB。架构从 `浏览器 → 后端 → AI API → 数据库` 塌缩成**浏览器同时是应用运行时、推理引擎和数据存储**。作者一个刻意的取舍值得注意：**核心助手完全不接外部工具**——因为每个外部工具都是一道数据可能离开设备的边界，而且轻量本地模型也扛不住复杂的工具调用 schema。fork + 改 `config.json` + GitHub Pages 就是你自己的私有助手
- [用 WebLLM + WebGPU 做零延迟的浏览器端问诊助手](https://dev.to/wellallytech/your-browser-is-the-new-doctor-building-a-zero-latency-private-ai-symptom-screener-with-webllm--3og9) — Vite + TS + `@mlc-ai/web-llm` 的完整实操，包含一个容易被忽略的工程细节：**在拉 2GB 权重之前先探测 WebGPU 可用性**（`navigator.gpu.requestAdapter()`），不支持则降级到 WASM/CPU。对前端来说这是最短的「把模型跑起来」路径，也是把「流式渲染 + 加载进度 + 降级策略」这些老本行直接变现的场景

## 今日值得深入

**1. 把 Muse Glimmer 30B + AMD 记忆蒸馏 + CoBa 算力路由当成一套栈来读**

这三篇昨天同时落地，恰好是本地 Agent 栈的三层：[Muse Glimmer 30B](https://huggingface.co/meta-models/Muse-Glimmer-30B) 解决「本地有没有能打的 agent 模型」（MCP-Atlas 75.5，18–20GB，M4 Max 能跑）；[AMD](https://arxiv.org/abs/2608.07169) 解决「小模型怎么补上经验」（免训练，靠大教师的 Workflow/Subtask/Function 三层记忆，4B 学生受益最大，AppWorld +27.2pp）；[CoBa](https://arxiv.org/abs/2608.07424) 解决「本地算力怎么花」（便宜验证广撒网 + 强验证兜高价值，token 省 49.1% 而准确率不掉）。

对你现在那套 light=qwen2.5:7b / heavy=deepseek-r1:32b / cloud fallback 的三层路由，这三篇分别对应三个可落地的改造点：**换基座**（Muse Glimmer 的 MCP-Atlas 分数意味着它在工具调用上大概率强过 qwen2.5:7b）、**加记忆层**（AMD 的 Function memory「报错时才反应式检索」是个成本极低的增量——你已有的 ToolExecutor 错误路径就是天然挂载点）、**改路由判据**（CoBa 把路由从「按任务难度选模型」升级成「按边际算力价值决定继续生成 / 转去验证 / 直接停止」，这是比 TokenBudget 预检查更靠后也更有效的一道闸）。

**2. [DCAS: 把「规划」从脚手架产物变成模型能力](https://arxiv.org/abs/2608.06113) —— 这篇直接打在 harness engineering 的靶心上**

它证明了一件你在 pi harness 实践中大概率已经隐约感觉到的事：**当前开源 CLI agent 的能力，有相当一部分不属于模型，而是被脚手架的约定托着的**。因为微调数据几乎全采自 OpenHands，换个脚手架就掉分，而未微调的基座模型反而没这个问题——**退化是微调引入的**。

作者对「规划」的二分特别值得记：**显式规划**是执行前产出的一等公民计划产物，**隐式规划**是贯穿整个 agent 循环的结构性约定。你写 AGENTS.md、定 skill 格式、约定 prompt 骨架，做的其实全是隐式规划。这篇的结论是这部分**可以也应该被内化进模型**，而不是永远靠 harness 兜着。DCAS 那层「不改脚手架的后端替换拦截层」本身也是个可复用的设计——**任意 CLI 脚手架 × 任意后端模型的自由组合**，正好是做跨 harness 对比评测时最缺的基础设施。
